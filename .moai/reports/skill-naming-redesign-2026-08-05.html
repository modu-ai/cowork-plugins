요약: 스킬명을 <domain>-<specialty> 단일 규칙으로 통일하고, 직관성을 해치는 4가지 문제를 고친다 — ① business- 접두사 5개 플러그인 혼용(과적하) ② office- 3곳 혼용 ③ moai-adk 레거시(moai-domain-*, moai-workflow-*, 불투명 cd-*) ④ general-*/중복명/난해명. design-landing-motion은 코더로 이동 확정.

1스킬명 구조 정의 (Naming Convention v1)

형식: <domain>-<specialty> — kebab-case, 소문자. domain은 영역, specialty는 구체 역할.

규칙 1. kebab-case 소문자 only. (landing-page-motion ◯ / LandingPageMotion ✗)
규칙 2. 플러그인명 접두사 금지 — 플러그인 디렉토리가 이미 네임스페이스. (moai-domain-copywriting ✗ → design-copywriting)
규칙 3. 불투명 약어·레거시 토큰 금지 — cd-, gan, domain, workflow(moai-adk 찌꺼기)는 풀어쓰거나 진짜 domain으로 교체.
규칙 4. domain 1:1 전담 — 한 domain은 원칙적으로 한 플러그인이 전담. 중복 혼용(business-, office-) 금지. 크로스-플러그인 충돌은 plugin:skill 호출 prefix로 해소.
규칙 5. 이름만으로 역할 드러낼 것(직관성). project(bare) ✗, general-feedback(모호) ✗.
규칙 6. 플러그인 내 유일. (예외: 플랫폼명 instagram-*/threads-*는 직관적이라 domain 규칙보다 우선 허용)

4우선 정리 대상 (영향 큰 순)

P0 — moai-adk 레거시 (designer 11개)

6마이그레이션 참고

이름 변경 시 하위호환

스킬명(디렉토리명) 변경은 기존 호출(moai-x:old-name)을 깬다. 대응: ① 각 SKILL.md frontmatter name 유지 + aliases 추가, 또는 ② 일괄 rename을 별도 마이그레이션 SPEC(한 번에)으로 실행 + 사용자 문서/예시 갱신. cross-reference(moai-media:media-higgsfield-* 등) 내부 참조도 같이 수정 필요.

7결정 필요 사항 (사용자)

  1. 이 재설계 안을 채택할까? (P0~P2 전부, 또는 P0[레거시]만 먼저)
  2. education- → edu- 축약 적용? (가독성 ↑, 안정성 ↓)
  3. analyst 중복 4쌍 — run 전 역할 비교해서 통합/삭제 진행?
  4. 이름 변경을 어떻게 실행할까? — 일괄 rename SPEC(별도) vs 코더 플러그인 SPEC과 함께 진행 vs 단순 제안에 그칠지
  5. ? 표시 제안(desc 미확정 ~7개) — 개별 확정 필요
